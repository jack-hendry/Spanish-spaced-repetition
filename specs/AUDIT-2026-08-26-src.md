# Source audit — `web/src` + `server/src`

**Date:** 2026-08-26
**Scope:** every file under `web/src/` and `server/src/` (11,797 lines, 88 files).
**Baseline:** `npm run test` — 37 server tests + 183 web tests, all passing. `npm run build` clean.

## Verdict

The codebase is in better shape than "we didn't use the AI infrastructure" implies. Zero `any`,
zero `TODO`/`FIXME`, one `console.log` (the bootstrap catch), consistent Angular-22 idiom
(standalone + signals + `inject()`, no `.subscribe()` anywhere), pure logic separated into
`core/*.ts` with colocated specs, and genuinely good architectural comments. The
scheduling-lives-in-the-frontend split described in `CLAUDE.md` is real and is honoured.

The problems are concentrated in four places: **six concrete bugs** (three verified by
executing them), **an unenforced tooling floor** (no linter at all, `strict` off), **config
fields that exist in the model and the UI but are never read**, and **copy-paste between the
three components that render stats**.

Findings are ordered by severity. Every file:line was read; the three tagged **VERIFIED**
were reproduced with a throwaway spec that was then deleted.

## 1. Confirmed bugs

### B1 — Shortening learning steps produces `due: NaN` — **HIGH** — VERIFIED

`web/src/app/core/scheduling/sm2.ts:141-143` and `web/src/app/core/scheduling/fsrs.ts:160-162`

```ts
const nextLeft = curLeft - 1;
const nextStep = steps.length - nextLeft;
good = this.learningStep(card, ctx, nextLeft, steps[nextStep], 'learning');
```

`curLeft` comes from the card's persisted `card.left`; `steps` comes from the *current* deck
options. When a user edits Options and removes a learning step, any card mid-learning has
`card.left > steps.length`, so `nextStep` goes negative, `steps[-1]` is `undefined`, and
`due: ctx.now + undefined * 60_000` is `NaN`.

A card with `due: NaN` fails every comparison in `StudyQueueService.next()`
(`NaN <= ctx.now` is false), so it silently disappears from the study queue — forever, and
with no error. `NaN` also survives `JSON.stringify` as `null`, so `cards.json` gets a `null`
due on the next debounced write.

The `hard` branch two lines above guards this exact case with `Math.max(0, ...)`
(`sm2.ts:132`, `fsrs.ts:146`); the `good` branch does not. Both schedulers have the identical
defect, which is what you'd expect from one being written by copying the other.

Reproduction (steps `[1,10,60]` → `[1]`, card with `left: 3`):

```
SM2  good.due = NaN   label = NaN
FSRS good.due = NaN   label = NaN
```

**Fix:** clamp the same way `hard` does — `const nextStep = Math.max(0, Math.min(steps.length - 1, steps.length - nextLeft));`
and clamp `curLeft` to `steps.length` on entry. Anything touching this is **Large** per the
task-sizing rule; add the case to `sm2.spec.ts` / `fsrs.spec.ts`.

### B2 — Browse shows epoch-ms as a day count for suspended learning cards — **MEDIUM** — VERIFIED

`web/src/app/core/stats.ts:230-240`

```ts
if (card.queue === 'new') return '—';
if (card.queue === 'learning') { /* treat due as epoch ms */ }
const diffDays = Math.max(0, card.due - today);   // treats due as a day number
```

The function branches on `queue`, but `card.due`'s unit is set by the card's *type*. A card
that lapsed and was then suspended (the leech path, `sm2.ts:209`) has `type: 'relearning'`,
`queue: 'suspended'`, and `due` in **epoch milliseconds** — it falls through to the day-number
branch. Same for a buried relearning card (`schedBuried` / `userBuried`).

Reproduction: `formatRelativeDue({type:'relearning', queue:'suspended', due:1787000000000}, 100, now)`
returns `"1786999999900 days"`, which is what the Browse table renders.

This is exactly the `card.due`-overloading trap the `scheduling-domain` skill warns about, and
the leech path is the one that reliably creates the state.

**Fix:** branch on `card.type`, not `card.queue`. Note `pause-shift.ts:14` already documents
"Rule is selected by `card.type` (never `card.queue`)" — this file just didn't get the memo.

### B3 — Review picks the card template by array index, not by `ord` — **MEDIUM**

`web/src/app/features/review/review.ts:201-204`

```ts
const template = noteType.kind === 'cloze'
  ? noteType.templates[0]
  : noteType.templates[card.ord] ?? noteType.templates[0];
```

`card.ord` is a template **ord**, not a position in the `templates` array. Everywhere else in
the codebase builds a lookup — `generate.ts:88` (`templateByOrd`), `transform.ts:157`
(`templateByOrd`). Only the review screen assumes `templates[i].ord === i`.

Today that assumption holds, because `migrations.ts:68` appends the Listening template (ord 1)
to a one-template note type. It breaks the moment a template is removed or inserted out of
order — and it breaks *silently*, by rendering the wrong side of the wrong card.

**Fix:** `noteType.templates.find(t => t.ord === card.ord) ?? noteType.templates[0]`.

### B4 — The global keydown handler steals keys from the type-in input — **MEDIUM**

`web/src/app/features/review/review.ts:57` + `300-330`, template at `review.html:59-68`

`host: { '(document:keydown)': 'onKey($event)' }` fires for every keystroke on the document,
including ones typed into the `{{type:}}` answer `<input>`. `onKey` handles `-` before it
checks whether the card is type-in:

```ts
if (e.key === '-') { e.preventDefault(); void this.suspend(); return; }
```

So typing a hyphen while answering a type-in card — plausible in Spanish text — **suspends the
card** and advances. `Escape` (line 302) likewise navigates to `/` mid-answer rather than
blurring the field. The `!this.revealed()` branch below already reasons carefully about
type-in for Space vs Enter (line 312-320); `-` and `Escape` sit above that check and never got
the same treatment.

**Fix:** early-return from `onKey` when `e.target` is the type-in input (or when
`state()?.isTypeIn && !revealed()`), except for a deliberate blur on Escape.

### B5 — Re-import restarts new-card queue positions at 0 — **MEDIUM**

`server/src/import/transform.ts:148` (`let newCardPosition = 0;`) and `:212` (`due: newCardPosition++`)

Cards that already exist keep their `due` (`transform.ts:197-203`), but every card the import
newly creates is numbered from 0. So after `npm run import` adds content to a collection whose
existing new queue runs to, say, 4,000, the fresh cards get positions 0..N and **jump ahead of
every card already waiting** in the new queue — `StudyQueueService.next()` step 3 sorts on
`due` ascending (`study-queue.service.ts:118`).

Both other card-creating paths get this right and compute the next free slot first:
`routes/index.ts:20` and `migrations.ts:38`, the latter with a comment explicitly calling out
that positions must not collide. The importer is the one that doesn't.

**Fix:** seed `newCardPosition` from `max(existing.cards.filter(queue === 'new').due) + 1`,
reusing the `nextNewPosition` helper.

### B6 — Study sessions ignore `collection.defaultDeckOptionsId` — **MEDIUM**

`web/src/app/core/study-queue.service.ts:48-49` and `:66`

```ts
const opts = this.store.optionsFor(deck) ?? this.store.deckOptions()[0];   // start()
const opts = this.store.deckOptions()[0];                                  // startAll()
```

`Collection.defaultDeckOptionsId` exists (`models/index.ts:15`), is seeded to `'opts-default'`
(`seed.ts:71`), and is never read by anything. Both call sites use "whichever options group
happens to be first in the array" instead. `startAll()` — the "study all decks" path — *always*
does, even when the deck has its own options. Add a second options group and the array order
decides your daily limits and your scheduler.

**Fix:** resolve through `defaultDeckOptionsId`, falling back to `[0]`.

## 2. Correctness and robustness

### C1 — Unescaped attribute interpolation in the importer — **MEDIUM**

`server/src/import/transform.ts:93`

```ts
return ok ? `<img src="${url}">` : '';
```

The URL is interpolated into an HTML attribute with no escaping. `isUrl` only requires
`^https?://\S+$`, and `"` is not whitespace, so a source URL containing a double quote closes
the attribute and everything after it parses as further attributes. Combined with §C2 below
(the SPA renders card HTML via `bypassSecurityTrustHtml`) that is script execution from
scraped/`.apkg` content.

The sibling function `transformMedia` in `template-renderer.ts:114-117` **does** escape:
`url.trim().replace(/"/g, '&quot;')`. The audio path is defended, the image path isn't — the
inconsistency is the tell.

**Fix:** escape `"`, `<`, `>` in `mediaImage` the same way `transformMedia` does.

### C2 — All card content is rendered through `bypassSecurityTrustHtml` — **MEDIUM**

`web/src/app/features/review/review.ts:233-237`

```ts
return this.sanitizer.bypassSecurityTrustHtml(
  `<style>${css}</style><div class="card">${body}</div>`,
);
```

Both the note-type CSS and the rendered card body bypass Angular's sanitizer wholesale. This is
a deliberate trade-off — Anki templates legitimately need `<style>` and arbitrary markup, and
sanitizing would break them — but it means content is trusted end-to-end, and the only defence
is whatever the import path escapes. Given §C1, that defence has a hole.

For a local single-user app the practical risk is low. Worth recording as an accepted risk
(an `AD-NNN` entry) rather than leaving it implicit, and worth fixing C1 so the trust boundary
is actually held at import time.

### C3 — Optimistic updates never roll back — **MEDIUM**

`review.ts:271-280`, `collection.store.ts:186-285`, `browser.ts:400-409`

The pattern throughout is: mutate the signal, then `await` the HTTP call. No `catch`, no
rollback, no user-visible error.

```ts
this.store.applyCard(next);
this.queue.onAnswered(current.card);
this.answeredCount.update((n) => n + 1);
await lastValueFrom(this.api.submitReview(next, revlog));   // throws => state already advanced
```

If the server is down, the UI reports the review as recorded and moves on; the review is lost
on reload. `store.error` (`collection.store.ts:55`) exists but is only ever set by `load()` —
no mutation path writes to it, and no template renders an error for a failed write. `rate()`,
`suspend()`, `save()` (options), and `saveEdit()` (browser) all have `try/finally` with no
`catch`.

`unburyForNewDay` (`collection.store.ts:267-285`) is the sharpest case: it advances
`lastUnburyDay` unconditionally after a `Promise.all` of per-card PATCHes, so a partial failure
leaves cards buried with the checkpoint already moved past them — they stay buried until the
*next* day rollover.

### C4 — `applyResume` ignores the server's `applied: false` — **LOW**

`web/src/app/core/pause.service.ts:85-96`

The resume endpoint has an explicit no-op guard and returns `{ applied: false }` when the pause
episode is stale (`routes/index.ts:66-68`, spec R11b). The client discards the response and
unconditionally clears `pausedAt` locally *and* applies `cardUpdates` to the cached cards. In
the stale case the server wrote nothing, so the local cache is now shifted relative to disk
until the next reload.

The server side of this feature is unusually careful — the write-ordering comment at
`routes/index.ts:48-55` is excellent. The client just doesn't read the answer it's given.

**Fix:** `const { applied } = await lastValueFrom(...); if (!applied) { /* refresh from server */ return; }`

### C5 — Debounced write failures are silently swallowed — **LOW**

`server/src/store/file-store.ts:160-163`

```ts
setTimeout(() => {
  this.pending.delete(name);
  void this.flush(name);          // rejection is discarded
}, this.debounceMs);
```

`saveCardsSoon()` is the hot path for every review. A failed write (disk full, permissions)
produces no log line and no error anywhere — the API already returned 200. Add a `.catch()`
that at minimum logs.

### C6 — Request bodies are cast, never validated — **LOW** (local-only app)

`server/src/routes/index.ts:41`, `:100`, `:113`, `:135`

Every handler does `req.body as Partial<X>` and merges. `PATCH /cards/:id` will write any
field a client sends — `due`, `queue`, `type`, `interval` — with no check that the value is a
number or that `due`'s unit matches the queue. `POST /notes` (`:135`) pushes a client-supplied
note object straight into `notes.json` without generating `id`/`guid`/`created` or checking for
a duplicate id.

`PATCH /collection` (`:43`) guards `schemaVersion` specifically (and has a test for it at
`notes.integration.test.ts:134`) but nothing else, so a client can add arbitrary keys to
`collection.json`. (I checked the `__proto__` prototype-pollution variant against Node — it
does **not** reproduce here.)

This is fine for `localhost`, and `cors()` is wide open on the same reasoning. It stops being
fine the moment `specs/011-mobile-remote-access/` ships. Flagging it now so that spec can
budget for it.

### C7 — `POST /api/import` is destructive, unauthenticated, and blocks the event loop — **LOW**

`server/src/routes/index.ts:218` → `import/run.ts:14-22`

`transformBooks` rebuilds `decks`/`notes`/`cards` from `_source/` and `replaceAll` writes the
lot. Any note not present in the source files is deleted along with its cards and their
scheduling state. There is no dry-run, no backup, and no confirmation — one HTTP POST with an
empty body does it. `loadSourceBooks` also uses `readdirSync`/`readFileSync`, so the whole
import blocks the event loop.

### C8 — Bury and unbury issue one HTTP request per card — **LOW**

`collection.store.ts:236-239` and `:276-280`

`Promise.all(targets.map(c => api.patchCard(...)))`. On the first study of a new day this fires
one request per buried card — potentially hundreds in parallel, each triggering a debounced
`cards.json` rewrite. A bulk `PATCH /cards` endpoint would collapse it to one round-trip and
make the partial-failure problem in §C3 go away at the same time.

## 3. Declared but never implemented

These fields exist in **both** model files, are seeded, and in one case are exposed in the UI —
but nothing reads them. Each one is a promise the app doesn't keep.

| Field | Declared | Surfaced to user | Read by |
|---|---|---|---|
| `lapse.leechAction: 'tagOnly'` | `models/index.ts:138` | **Yes** — `options.html:128` | nothing |
| `display.buryInterdaySiblings` | `models/index.ts:172` | no | nothing |
| `display.newGatherOrder` | `models/index.ts:168` | no | nothing |
| `display.newSortOrder` | `models/index.ts:169` | no | nothing |
| `display.reviewOrder` | `models/index.ts:170` | no | nothing |
| `new.insertionOrder` | `models/index.ts:150` | no | nothing |
| `collection.defaultDeckOptionsId` | `models/index.ts:15` | no | nothing — see **B6** |

`leechAction: 'tagOnly'` is the worst of these: the user can select "Tag only" in Options and
save it, and the setting does nothing at all. `sm2.ts:198` and `fsrs.ts:220` both compute
`isLeech` and then only act on it when the action is `'suspend'` — so choosing "Tag only" means
leeches are neither tagged nor suspended, i.e. silently ignored.

**Also unused:**

- `stats.ts:159 yearlyHeat()` — dead code. Referenced only by its own spec
  (`stats.spec.ts:159-172`). `buildHeatGrid` in `heatmap.ts` does the real work by a different
  method (see §D2).
- `Collection.schemaVersion` — preserved and tested, but never read to gate anything.
  `migrateAddListeningTemplate` re-scans every card and note on **every boot** with no version
  check. That's O(cards) per start today and an accumulating pile of hardcoded, single-purpose
  migrations tomorrow. Gating on `schemaVersion` is what the field is for.
- `collection.store.ts:56` — `this.cards().length >= 0` in the `loaded` computed is always
  true. Harmless, but it means `loaded` doesn't mean what it looks like it means.

## 4. Duplication

### D1 — Three components hand-roll the same stats plumbing

`app.ts`, `features/deck-list/deck-list.ts`, `features/stats/stats.ts`:

- `formatDuration(ms)` — **byte-identical** in `deck-list.ts:152-160` and `stats.ts:610-618`.
- `retention` computed — identical formula and comment, `deck-list.ts:107-112` and
  `stats.ts:601-606`. Each comment says "same formula as" the other, which is the code asking
  to be extracted.
- `today` / `reviewDays` / `heatTimestamps` / `dayTimes` — the same four `computed()` blocks,
  copied verbatim, `deck-list.ts:80-98` and `stats.ts:501-518`. Both carry the same "same idiom
  as [the other file]" comment.
- `totalDue` computed — identical in `app.ts:44-47` and `deck-list.ts:42-45`.

`core/stats.ts` is already the home for exactly this. The pure helpers there are well-factored;
the day-mapping wrapper around them just never made it out of the components.

### D2 — Two different day-bucketing implementations, one against the documented rule

`CLAUDE.md` and the `scheduling-domain` skill both state: *"Any 'per day' feature (limits,
unburying, heatmap buckets, forecast) must go through `todayNumber`, never through calendar
dates."*

- `core/stats.ts:159 yearlyHeat()` follows the rule — day numbers. **Unused.**
- `core/heatmap.ts:38 heatDateKey()` builds `YYYY-MM-DD` strings from `new Date(...)` local
  getters, and `buildHeatGrid` walks a calendar cursor. **This is what actually renders**, in
  both `deck-list` and `stats`.

The heatmap re-derives the cutoff-hour shift itself (`heatmap.ts:35`) instead of reusing
`todayNumber`, which is precisely the divergence that produced
`specs/archive/2026-07-14-007-heatmap-date-off-by-one`. Either delete `yearlyHeat` and document
why the heatmap is exempt (it needs calendar alignment for a Sun-anchored grid — a legitimate
reason), or rebuild the grid on day numbers. Right now the repo contains both answers and a
rule that contradicts the one in use.

### D3 — Deck hierarchy is derived from name strings in five places

`Deck.parentId` exists (`models/index.ts:127`) and is populated by the importer
(`transform.ts:123`). But every consumer splits on `'::'` instead:

`collection.store.ts:89` (depth), `:100-112` (ancestor rollup), `app.ts:35-40` (visibility),
`:96-97` (leaf name), `study-queue.service.ts:41-45` (subtree via `startsWith`),
`review.ts:91`, `:227`, `browser.ts:321`.

Two sources of truth for the same tree. If a deck is ever renamed without its children being
renamed in lockstep, `parentId` and the name prefix disagree and the counts silently go wrong.

### D4 — `nextNewPosition` duplicated

`routes/index.ts:20` and `migrations.ts:38`. The duplication is deliberate and the comment says
so ("kept local — the migration must not depend on the route module"), which is fair. But the
right home is `cards/generate.ts` next to `buildNewCard`, where the importer could use it too
and **B5** wouldn't exist.

## 5. Tooling and configuration

### T1 — There is no TypeScript linter — **MEDIUM**

No `eslint.config.*`, no `.eslintrc*`, at either workspace or repo root. `prettier` is a
devDependency of `web` but is not in any npm script and is not run by CI. `.github/workflows/ci.yml`
runs `tests`, `build`, `clean-table-check.sh`, the hook matrix, and `ruff` — **`ruff` lints the
Python tooling, and nothing lints the 11,797 lines of TypeScript that are the actual product.**

The code is clean enough that a linter would find little today. That's the argument *for*
adding it now — the floor is currently held by discipline alone, and the repo's whole premise
is putting guardrails under discipline.

**Suggested:** `angular-eslint` + `@typescript-eslint` recommended, `prettier --check`, both
wired into the existing `lint` CI job.

### T2 — `web` compiles without `strict` — **MEDIUM**, and free to fix

`web/tsconfig.json` sets `noImplicitOverride`, `noPropertyAccessFromIndexSignature`,
`noImplicitReturns`, `noFallthroughCasesInSwitch` — but **not** `"strict": true`, and
`angularCompilerOptions` has `strictInjectionParameters` and `strictInputAccessModifiers` but
**not** `"strictTemplates": true`. That's the Angular CLI default preset with the two most
important flags removed.

`server/tsconfig.json:7` has `"strict": true`. So the two workspaces disagree about whether
`null` is a type error.

I ran `tsc -p tsconfig.app.json --noEmit --strict` against the web workspace: **0 errors.** The
code already satisfies strict mode. Turning it on costs nothing and stops the next `undefined`
from getting through. `strictTemplates` needs a separate `ng build` check but is very likely
close.

### T3 — Toolchain versions diverge across workspaces — **LOW**

| | web | server |
|---|---|---|
| TypeScript | `~6.0.2` | `^5.7.2` |
| vitest | `^4.0.8` | `^2.1.8` (resolved 2.1.9) |

Two TypeScript compilers and two test runners in one repo. `web/src/app/core/models/` and
`server/src/models/index.ts` are declared to be a mirrored contract that must be changed
together — and they're type-checked by different compilers. Align both.

### T4 — No error surface for any write — **LOW**

Covered mechanically in §C3; noting it here as a product gap too. `store.error` is rendered by
the shell (`app.ts:22`) but only `load()` ever sets it. Every failed review, note edit, options
save, and suspend fails silently.
